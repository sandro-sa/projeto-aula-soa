Criar os primeiros POMs do zero

Criar a configuração inicial do projeto e abri-la no Eclipse.

1. O que fazer nesta etapa

Sua tarefa é criar três arquivos na pasta laboratorio-restaurante-soa:

  1. pom.xml
  2. source/restaurante-soap/pom.xml
  3. scripts/maven.ps1

Depois, valide os dois POMs e importe os projetos no Eclipse. A aula termina quando os dois comandos mostrarem BUILD SUCCESS e os projetos aparecerem na IDE.

Continue na pasta usada na aula 11. Os documentos anteriores permanecem nela. A criação das classes começa na aula 13.

2. Entenda os três arquivos

O POM é o arquivo pom.xml que descreve um projeto para o Maven. Os dois POMs desta aula têm funções diferentes:

O que você vai criar
Arquivo Para que serve
pom.xml na raiz Organiza a execução do Maven e inclui o projeto da pasta source/restaurante-soap.
source/restaurante-soap/pom.xml Define Java 17, versões e ferramentas que os futuros módulos SOAP vão herdar.
scripts/maven.ps1 Auxilia a chamada do Maven usando um cache dentro do laboratório. Será útil nas próximas etapas.

Atenção aos caminhos: os dois primeiros arquivos têm o mesmo nome, mas ficam em pastas diferentes. Ambos usam packaging igual a pom, pois nesta aula estamos criando a configuração dos projetos.

3. Faça o passo a passo

Passo 1: Abrir o laboratório e criar as pastas

  1. No Explorador de Arquivos, abra sua pasta laboratorio-restaurante-soa.
  2. Na barra de endereço, digite powershell e pressione Enter.
  3. Execute os comandos abaixo nesse terminal:
Get-Location
New-Item -ItemType Directory -Path '.\diagramas' -Force
New-Item -ItemType Directory -Path '.\docs' -Force
New-Item -ItemType Directory -Path '.\source\restaurante-soap' -Force
New-Item -ItemType Directory -Path '.\scripts' -Force

Confira: o caminho exibido deve ser o do laboratório. As pastas diagramas, docs, source/restaurante-soap e scripts devem aparecer no Explorador. Os comandos com -Force reaproveitam as pastas existentes.

diagramas/componentes.md vem da aula 10 e docs/camadas.md da aula 11. Preserve esses arquivos e acrescente os três arquivos desta etapa.

Nos próximos três passos, abra cada arquivo no Bloco de Notas. Se aparecer uma pergunta para criá-lo, escolha Sim. Cole o conteúdo e salve com Ctrl+S. Confira o nome indicado e use UTF-8.

Passo 2: Criar pom.xml na raiz

No mesmo PowerShell, abra o primeiro arquivo:

notepad '.\pom.xml'

Copie o conteúdo completo abaixo e salve. Os trechos <!-- ... --> são comentários: explicam o XML e podem ser copiados junto com ele.

<!-- project é a raiz do XML; xmlns identifica o formato de POM do Maven. -->
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <!-- Versão do formato do POM. Não é a versão do Maven instalado. -->
  <modelVersion>4.0.0</modelVersion>
  <!-- Identifica o grupo da instituição/projeto nas coordenadas Maven. -->
  <groupId>br.edu.soa</groupId>
  <!-- Nome do projeto agregador: organiza a execução do laboratório. -->
  <artifactId>laboratorio-restaurante</artifactId>
  <!-- Versão adotada para os artefatos do restaurante neste material. -->
  <version>2.0.0</version>
  <!-- Este projeto organiza/configura outros projetos; não produz JAR ou WAR. -->
  <packaging>pom</packaging>
  <!-- Lista os projetos incluídos no build; o caminho parte deste POM. -->
  <modules>
    <module>source/restaurante-soap</module>
  </modules>
</project>

Confira: este arquivo fica diretamente em laboratorio-restaurante-soa. A linha <module>source/restaurante-soap</module> inclui o projeto SOAP na execução.

Entenda os números: modelVersion = 4.0.0 identifica o formato XML do POM, inclusive quando usamos Maven 3. Já version = 2.0.0 é a identificação escolhida pelo material para o projeto do restaurante. Os futuros módulos usam essa mesma versão ao indicar seu POM pai. Veja a referência do POM.

Passo 3: Criar source/restaurante-soap/pom.xml

Abra o segundo POM:

notepad '.\source\restaurante-soap\pom.xml'

Copie o bloco completo abaixo e salve. As configurações de versões e ferramentas serão aproveitadas pelos módulos nas próximas aulas.

<!-- project é a raiz do XML; xmlns identifica o formato de POM do Maven. -->
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <!-- Versão do formato do POM. Não é a versão do Maven instalado. -->
  <modelVersion>4.0.0</modelVersion>
  <!-- Identifica o grupo da instituição/projeto nas coordenadas Maven. -->
  <groupId>br.edu.soa</groupId>
  <!-- Nome do POM pai que os futuros módulos SOAP vão herdar. -->
  <artifactId>restaurante-soap</artifactId>
  <!-- Versão adotada para os artefatos do restaurante neste material. -->
  <version>2.0.0</version>
  <!-- Este projeto organiza/configura outros projetos; não produz JAR ou WAR. -->
  <packaging>pom</packaging>
  <!-- Fica vazio agora. Adicionaremos dominio e os demais módulos nas respectivas aulas. -->
  <modules>

  </modules>
  <!-- Valores reutilizáveis. A escrita ${nome} consulta uma propriedade. -->
  <properties>
    <!-- Compila fontes e APIs para Java 17. Não instala nem seleciona o JDK. -->
    <maven.compiler.release>17</maven.compiler.release>
    <!-- Preserva nomes de parâmetros no bytecode para uso por reflexão. -->
    <maven.compiler.parameters>true</maven.compiler.parameters>
    <!-- Padroniza a codificação dos arquivos-fonte, inclusive os acentos. -->
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <!-- Versão fixada da implementação SOAP Metro, usada em jaxws-rt. -->
    <metro.version>4.0.5</metro.version>
    <!-- Versão do catálogo de dependências (BOM) usado pelo projeto SOAP. -->
    <spring-boot.version>3.5.16</spring-boot.version>
  </properties>
  <!-- Define versões padrão. Cada módulo ainda declara as dependências que usa. -->
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>org.springframework.boot</groupId>
        <!-- BOM: catálogo que alinha versões do driver MySQL, Flyway e JUnit. -->
        <artifactId>spring-boot-dependencies</artifactId>
        <version>${spring-boot.version}</version>
        <!-- Importamos um documento POM de configuração. -->
        <type>pom</type>
        <!-- Incorpora o catálogo do BOM ao dependencyManagement deste projeto. -->
        <scope>import</scope>
      </dependency>
      <dependency>
        <groupId>com.sun.xml.ws</groupId>
        <!-- Implementação Metro que executa serviços e clientes SOAP. -->
        <artifactId>jaxws-rt</artifactId>
        <version>${metro.version}</version>
      </dependency>
      <dependency>
        <groupId>jakarta.xml.ws</groupId>
        <!-- API Jakarta XML Web Services: tipos como Service e Endpoint. -->
        <artifactId>jakarta.xml.ws-api</artifactId>
        <version>4.0.2</version>
      </dependency>
      <dependency>
        <groupId>jakarta.jws</groupId>
        <!-- API de anotações como WebService, WebMethod e WebParam. -->
        <artifactId>jakarta.jws-api</artifactId>
        <version>3.0.0</version>
      </dependency>
    </dependencies>
  </dependencyManagement>
  <!-- Configuração das ferramentas de compilação, testes e empacotamento. -->
  <build>
    <!-- Centraliza versões/opções de plugins usados pelos módulos; não agenda tarefas. -->
    <pluginManagement>
      <plugins>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <!-- Compila o Java; lê maven.compiler.release e maven.compiler.parameters. -->
          <artifactId>maven-compiler-plugin</artifactId>
          <version>3.14.0</version>
        </plugin>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <!-- Executa os testes unitários na fase test dos módulos com esse ciclo. -->
          <artifactId>maven-surefire-plugin</artifactId>
          <version>3.5.3</version>
          <!-- Opções específicas do plugin Surefire. -->
          <configuration>
            <!-- Usa classpath nos testes, conforme a organização sem JPMS deste laboratório. -->
            <useModulePath>false</useModulePath>
          </configuration>
        </plugin>
        <plugin>
          <groupId>org.apache.maven.plugins</groupId>
          <!-- Empacota a aplicação web em WAR para implantação no Tomcat. -->
          <artifactId>maven-war-plugin</artifactId>
          <version>3.4.0</version>
        </plugin>
        <plugin>
          <groupId>org.codehaus.mojo</groupId>
          <!-- Permite chamar uma classe main com exec:java, por exemplo a tela Swing. -->
          <artifactId>exec-maven-plugin</artifactId>
          <version>3.5.0</version>
        </plugin>
      </plugins>
    </pluginManagement>
    <!-- Declara plugins herdáveis; o Surefire usa a versão/opções definidas acima. -->
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <!-- Executa os testes unitários na fase test dos módulos com esse ciclo. -->
        <artifactId>maven-surefire-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>

Confira: o artifactId é restaurante-soap. O bloco <modules> fica vazio: cada módulo será acrescentado na aula em que for criado.

Como as versões são escolhidas: a linha principal de cada ferramenta atende à tecnologia usada; o número exato fica fixado para todos seguirem a mesma configuração do laboratório. Por exemplo, Java 17 não exige especificamente o Compiler Plugin 3.14.0: esse é o número adotado nesta base.

Por que usamos cada versão deste POM?
Função e motivo das versões adotadas no laboratório
Item e versão Por que usamos
Java 17 É o alvo comum do laboratório, permite os record usados no domínio e atende à base Java 17 da linha Boot 3.5. A propriedade release restringe linguagem, bytecode e APIs Java ao alvo. Compilação para uma versão Java.
Metro 4.0.5 A linha 4 trabalha com Jakarta XML Web Services 4 e a integração com Tomcat 10.1. Mantemos a revisão 4.0.5 da base, que inclui correções e atualização do JAXB. Documentação da linha 4 e notas da 4.0.5.
Spring Boot BOM 3.5.16 Fornece o catálogo de versões usado pelos módulos SOAP, incluindo bibliotecas de persistência e testes. Aqui usamos seu BOM; o servidor SOAP continua com Metro e Tomcat. A aplicação REST terá seu próprio POM do Initializr. Dependências gerenciadas e requisitos Java.
jakarta.xml.ws-api 4.0.2 É a API da especificação XML Web Services 4.0 usada pela família Metro 4. A API fornece os tipos; Metro fornece a implementação. Especificação e coordenadas oficiais.
jakarta.jws-api 3.0.0 Fornece as anotações do pacote jakarta.jws. Essa API tem numeração própria e é usada junto com XML Web Services 4; seus números não precisam ser iguais aos de Metro. Especificação das anotações.
Compiler Plugin 3.14.0 Suporta a configuração release = 17. Fixamos essa versão da ferramenta para repetir a configuração de compilação nos módulos. Documentação da 3.14.0.
Surefire Plugin 3.5.3 É a versão fixada para executar os testes JUnit do laboratório. useModulePath = false mantém os testes no classpath, pois não usamos descritores module-info.java. Execução e opções de testes.
WAR Plugin 3.4.0 É a ferramenta de empacotamento fixada para o futuro módulo servidor, que terá packaging = war. Sua versão é independente da versão do Tomcat. Documentação da 3.4.0.
Exec Plugin 3.5.0 É a versão fixada para os comandos exec:java usados depois para abrir as aplicações Swing. Como executar uma classe Java.

As versões pontuais acima preservam a base do material. Compatibilidade depende da combinação de APIs, implementação, JDK e configuração; uma versão diferente também pode funcionar, após a validação correspondente.

Entenda properties, dependências e plugins sem confundir os blocos
  • properties: guarda valores reutilizáveis. ${metro.version} será substituído por 4.0.5. parameters = true preserva nomes para reflexão; UTF-8 padroniza a leitura dos fontes. Opções do compilador.
  • dependencyManagement: define versões padrão. Um módulo inclui uma biblioteca ao declará-la em seu próprio dependencies. O par type = pom e scope = import importa a lista de versões de um BOM. Gerenciamento de dependências.
  • pluginManagement: define versões e opções dos plugins usados pelo build. Listar um plugin nesse bloco não agenda uma tarefa; ele será usado quando o ciclo do módulo ou uma declaração/chamada o acionar. O plugins abaixo declara Surefire e reaproveita a configuração centralizada. Gerenciamento de plugins.
  • Agregação e herança: o modules da raiz inclui projetos na execução. Já o futuro parent dos módulos aponta para restaurante-soap para receber suas configurações. Estar em modules não cria herança automaticamente. Relações entre POMs.

Passo 4: Criar scripts/maven.ps1

Abra o arquivo do script:

notepad '.\scripts\maven.ps1'

Copie o conteúdo completo, incluindo os comentários numerados, e salve. Cada comentário explica uma etapa do script:

# 1. Recebe os argumentos escritos depois do nome do script.
# Exemplo: -N validate. As opções são repassadas ao Maven.
$argumentosMaven = @($args)

# 2. Se nenhum argumento foi informado, usa clean verify.
# clean limpa arquivos gerados; verify percorre o build e suas verificações.
if ($argumentosMaven.Count -eq 0) { $argumentosMaven = @('clean','verify') }

# 3. Interrompe o script se um comando do PowerShell gerar erro.
# O código de saída do Maven será conferido separadamente no passo 7.
$ErrorActionPreference = 'Stop'

# 4. Localiza a raiz do laboratório.
# PSScriptRoot é a pasta scripts; Split-Path -Parent obtém a pasta acima.
$raiz = Split-Path -Parent $PSScriptRoot

# 5. Guarda a pasta atual do terminal e entra na raiz do laboratório.
Push-Location -LiteralPath $raiz
try {
    # 6. Executa o Maven a partir da raiz.
    # & chama o comando mvn.
    # -Dmaven.repo.local escolhe onde guardar bibliotecas e plugins baixados.
    # @argumentosMaven repassa cada argumento como uma opção separada.
    & mvn "-Dmaven.repo.local=$raiz\.m2\repository" @argumentosMaven

    # 7. Confere se o Maven terminou com sucesso: código zero.
    # Um código diferente de zero gera um erro no script.
    if ($LASTEXITCODE -ne 0) { throw "Maven terminou com código $LASTEXITCODE" }
} finally {
    # 8. Ao sair do bloco try, retorna à pasta anterior, mesmo em caso de erro.
    Pop-Location
}

Confira: o nome deve ser maven.ps1, sem .txt no final. O script encaminha comandos ao Maven; a validação desta aula será feita diretamente com mvn, no passo seguinte.

Passo 5: Validar os dois POMs

Salve os três arquivos. No PowerShell, ainda na raiz do laboratório, execute primeiro:

mvn -N validate

Confira: deve aparecer BUILD SUCCESS. Esse comando valida o POM da raiz.

Depois, execute:

mvn -f source/restaurante-soap/pom.xml -N validate

Confira: deve aparecer outro BUILD SUCCESS. Agora o Maven validou o POM de restaurante-soap. Na primeira execução, ele pode baixar os arquivos necessários; aguarde o resultado final.

-f escolhe o POM; -N limita a execução ao projeto selecionado. validate verifica a configuração antes das fases de compilação e testes. Consulte, se precisar, as opções do Maven e o ciclo de execução.

Passo 6: Importar no Eclipse

  1. No Eclipse, acesse File → Import….
  2. Selecione Maven → Existing Maven Projects e clique em Next.
  3. Em Root Directory, clique em Browse… e escolha sua pasta laboratorio-restaurante-soa.
  4. Confira os dois POMs encontrados: o da raiz e o de source/restaurante-soap. Mantenha ambos selecionados.
  5. Clique em Finish e aguarde a importação.

Confira: o Project Explorer deve mostrar laboratorio-restaurante e restaurante-soap. Esses projetos contêm configuração; as classes Java serão criadas nas próximas aulas.

Se a validação ou a importação não der certo
  • Maven não encontra o POM: confira Get-Location e o nome do arquivo. Ele deve terminar em .xml, sem .txt.
  • Erro ao ler XML: compare o arquivo com o bloco completo do passo correspondente, incluindo as tags de abertura e fechamento.
  • Módulo não encontrado: o POM da raiz lista apenas source/restaurante-soap; o bloco modules do POM SOAP deve estar vazio.
  • Falha ao baixar dependências: confira a conexão com a Internet e repita o comando que falhou.
  • mvn não é reconhecido: retome a configuração do Maven e abra um terminal novo.
  • Eclipse não encontra os projetos: escolha a pasta do laboratório como Root Directory e confira se os dois POMs foram salvos.

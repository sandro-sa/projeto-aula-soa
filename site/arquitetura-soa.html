Desenhar as fronteiras SOA

Organizar capacidades do restaurante por contratos com responsabilidades claras.

1. Objetivo do tutorial

Ao final, você deverá conseguir desenhar e entender os limites entre os clientes, protocolos, adaptadores, regras de negócio e persistência. Você também saberá por que um pedido criado na versão SOAP não aparece automaticamente na REST.

Ideia central: compartilhar código Java não significa compartilhar estado, processos em execução ou tabelas no banco de dados.

2. Conceitos necessários

SOA e contrato

SOA organiza capacidades de negócio como serviços. O contrato descreve como o consumidor interage com cada capacidade, sem expor detalhes internos de tabelas.

SOAP, Metro e Tomcat

SOAP define a estrutura XML das mensagens; o WSDL descreve o contrato do serviço. O Tomcat hospeda a aplicação web e o Metro implementa a infraestrutura dos serviços SOAP.

REST e Spring Boot

Na outra versão, endpoints HTTP oferecem recursos e operações em JSON. O Spring Boot executa sua própria aplicação, separada da implantação SOAP.

Clean Architecture

Organiza as dependências internas: adaptadores chamam casos de uso; casos de uso aplicam as regras do domínio e dependem de interfaces (portas), não de JDBC diretamente.

Uma aplicação, vários tipos de cliente

Na versão SOAP, as telas Java Swing de administração e do garçom chamam serviços SOAP/XML. O cardápio acessado pelo celular chama um BFF Servlet que responde em HTTP/JSON. Na versão REST, o Swagger UI ou outro cliente HTTP acessa operações autenticadas de pedidos, enquanto o cardápio público consulta somente informações de produtos.

Não confunda: o cardápio do celular é apenas para consulta nesta implementação. Ele não cria pedidos, não adiciona itens e não fecha contas. A versão REST ainda não tem tela de garçom.

3. Problema que será resolvido

O restaurante precisa administrar mesas, categorias, produtos e pedidos sem permitir que cada interface acesse diretamente o MySQL ou implemente suas próprias regras. Além disso, queremos comparar dois estilos de integração - SOAP e REST - sem misturar os dados dos experimentos.

A solução é separar entrada (Swing, BFF, HTTP), regras de negócio (casos de uso e domínio) e saída (repositórios JDBC e MySQL).

4. Arquivos a criar ou alterar

Os caminhos partem da raiz de laboratorio-restaurante-soa, criada no tutorial inicial:

Este tutorial cria um diagrama e uma especificação de arquitetura; não pressupõe que todas as classes, bancos ou endpoints já estejam funcionando.

5. Implementação passo a passo e código da etapa

5.1. Criar a pasta do diagrama

No PowerShell, aberto na raiz do projeto:

New-Item -ItemType Directory -Path 'diagramas' -Force

No Eclipse: clique com o botão direito no projeto → New → Folder → diagramas. Depois use New → File para criar componentes.md.

Fundamentação nos PDFs fornecidos

Saudate discute contratos e reutilização entre capacidades; Martin discute dependências internas. No restaurante, quatro serviços compartilham regras e uma base transacional por implementação. Não se conclui que quatro WSDLs constituem quatro microsserviços.

  • [R01] Alexandre Saudate - SOA aplicado: integrando com web services e além. Cap. 1, §1.7–1.8: serviços e orientação a serviços. Páginas 27–29 do PDF.
  • [R01] Alexandre Saudate - SOA aplicado: integrando com web services e além. Cap. 7, §7.1–7.2: integração e modelo canônico. Páginas 200–203 do PDF.
  • [R03] Robert C. Martin - Arquitetura Limpa: o guia do artesão para estrutura e design de software. Cap. 22: regra de dependência e adaptadores. Páginas 273–282 do PDF.

Confira na leitura: Desenhe a diferença entre uma chamada remota e uma dependência de código-fonte.

A página é contada no arquivo PDF desde a capa. Critérios, adaptações e atualização dos exemplos.

6. Fluxo da execução

Consumidor → contrato → adaptador → caso de uso → porta de persistência → banco.

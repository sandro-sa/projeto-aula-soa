Criar a aplicação e seus erros

Prepare o módulo das regras de negócio e crie uma forma comum de informar por que uma operação do restaurante foi recusada.

1. O que fazer nesta etapa

Sua entrega é criar o módulo aplicacao, registrá-lo no pai e escrever Falha.java.

  1. Criar o módulo Maven aplicacao e conferir seu pom.xml.
  2. Conferir a entrada <module>aplicacao</module> no POM restaurante-soap/pom.xml.
  3. Criar Falha.java no pacote br.edu.soa.restaurante.aplicacao.
  4. Compilar pelo Maven dentro do Eclipse e obter BUILD SUCCESS.

Continue após a aula 19, com o módulo dominio pronto. As regras de mesas, produtos e pedidos serão implementadas nas próximas aulas; agora você prepara o módulo e o formato das suas falhas.

Dois arquivos com funções diferentes: o pom.xml configura como o Maven constrói o módulo; Falha.java será usado pelo código Java enquanto uma operação estiver sendo executada.

2. Qual problema Falha resolve no restaurante?

Imagine que o garçom tente alterar um pedido que já foi fechado. O sistema precisa recusar a alteração e explicar o motivo. Uma mensagem como “deu erro” não identifica o problema para a tela nem para os testes.

Falha reúne três informações sobre o mesmo problema:

InformaçãoExemploPara que serve
codigoPEDIDO_FECHADOIdentifica a situação específica. Consumidores e testes podem comparar esse identificador.
tipoCONFLITOClassifica o problema: a operação não pode ocorrer no estado atual do pedido.
mensagem“Pedido fechado não permite alterações.”Explica o motivo em linguagem compreensível para a pessoa que usa o sistema.

O código permite reconhecer o problema mesmo que o texto da mensagem seja melhorado. O tipo agrupa várias situações: MESA_OCUPADA e PEDIDO_FECHADO, por exemplo, são conflitos diferentes.

Como isso será usado nas próximas aulas:

  1. O garçom solicita a alteração de um pedido.
  2. Restaurante verifica o estado do pedido e, ao encontrar um impedimento, lança uma Falha.
  3. O fluxo normal daquela chamada é interrompido e chega ao tratamento de erro.
  4. O adaptador SOAP ou REST converte a falha para a resposta do serviço. A interface pode apresentar a mensagem.

Quem faz a verificação? A classe Restaurante, que você escreverá a partir da aula 22. Falha representa o problema encontrado; criar essa classe, sozinho, ainda não verifica um pedido nem impede uma gravação.

Ela fica no módulo aplicacao para ser compartilhada pelos casos de uso. Mais adiante, Acesso.java usará código e mensagem na resposta SOAP; Erros.java usará também o tipo para escolher o status HTTP. A regra de negócio comunica o motivo sem precisar construir XML ou uma resposta HTTP.

Por que algumas versões aparecem e outras não?

  • 2.0.0 identifica a versão dos artefatos do restaurante neste material. Deve coincidir com o pai e com os módulos usados; não indica uma versão de Java ou do Maven.
  • ${project.version} consulta a versão do módulo atual. Como aplicacao herda 2.0.0, a dependência de dominio também usa 2.0.0.
  • JUnit e Mockito não repetem uma tag version: recebem as versões gerenciadas pelo BOM importado no pai. O BOM é um catálogo de versões compatíveis entre si, adotado pelo laboratório.

Problema que este POM resolve: o Maven consegue localizar as dependências certas e compilar aplicacao com a mesma configuração dos demais módulos.

// Finalidade: representar uma falha da aplicação com código, tipo e mensagem.
// [1] O pacote corresponde às pastas br/edu/soa/restaurante/aplicacao.
package br.edu.soa.restaurante.aplicacao;

// [2] public: outros módulos podem usar esta classe.
// final: não permite criar subclasses de Falha.
// extends RuntimeException: permite lançar e capturar uma Falha como exceção.
public final class Falha extends RuntimeException {

    // [3] Categoria geral do problema. Para usar fora da classe: Falha.Tipo.
    public enum Tipo {
        VALIDACAO,       // A entrada não atende a uma regra.
        NAO_ENCONTRADO,   // O registro solicitado não existe.
        CONFLITO,        // O estado atual impede a operação.
        INTERNO          // Um problema técnico impediu a operação.
    }

    // [4] Dados adicionais da exceção.
    // private: acesso por métodos; final: atribuídos no construtor uma única vez.
    private final String codigo;
    private final Tipo tipo;

    // [5] Construtor: recebe os três dados de uma falha.
    public Falha(String codigo, Tipo tipo, String mensagem) {
        // Guarda a mensagem na parte herdada de RuntimeException.
        // Por isso podemos recuperá-la depois com getMessage().
        super(mensagem);
        // this.codigo é o campo; codigo é o argumento recebido.
        this.codigo = codigo;
        this.tipo = tipo;
    }

    // [6] Métodos de consulta dos campos privados.
    public String codigo() {
        return codigo;
    }

    public Tipo tipo() {
        return tipo;
    }

    // [7] Método de criação: chamado diretamente por Falha.invalido(...).
    // O chamador informa a mensagem; código e tipo são preenchidos aqui.
    public static Falha invalido(String mensagem) {
        return new Falha("ENTRADA_INVALIDA", Tipo.VALIDACAO, mensagem);
    }

    // [8] Um conflito pode ter códigos diferentes: MESA_OCUPADA, PEDIDO_FECHADO...
    // O tipo é fixo; o chamador informa o código específico e a mensagem.
    public static Falha conflito(String codigo, String mensagem) {
        return new Falha(codigo, Tipo.CONFLITO, mensagem);
    }
}

O que significa cada parte numerada?

ParteExplicação
1. packageIdentifica o pacote da classe e corresponde às pastas dentro de src/main/java. É por esse nome que outros módulos poderão importá-la.
2. public final class Falha extends RuntimeExceptionpublic permite o uso fora do pacote; final impede criar subclasses de Falha. A herança de RuntimeException faz dela uma exceção não verificada: os métodos não precisam declarar throws Falha para propagá-la. O lançamento ainda deve chegar a um tratamento adequado.
3. enum TipoDefine um conjunto de categorias permitidas. Por estar dentro da classe, é referenciado como Falha.Tipo, por exemplo Falha.Tipo.CONFLITO.
4. private finalprivate protege o acesso direto aos campos. final impede reatribuir codigo e tipo depois da construção do objeto.
5. Construtor, super e thisO construtor recebe os três dados. super(mensagem) entrega o texto ao construtor da superclasse. this.codigo = codigo copia o argumento para o campo do objeto; o mesmo vale para tipo.
6. codigo(), tipo() e getMessage()Os dois primeiros métodos devolvem os campos privados. getMessage() é herdado e recupera o texto enviado a super; por isso não criamos outro campo mensagem.
7. static Falha invalido(...)É um método de criação: pode ser chamado como Falha.invalido(...). Ele devolve uma nova falha com código ENTRADA_INVALIDA, tipo VALIDACAO e a mensagem recebida.
8. static Falha conflito(...)Também devolve um objeto, fixando o tipo CONFLITO. O código e a mensagem são argumentos porque há conflitos diferentes no restaurante.

Quando usar cada Tipo?

TipoSituação do restaurante
VALIDACAOQuantidade zero ou número de mesa fora do intervalo permitido. A entrada precisa ser corrigida.
NAO_ENCONTRADOO ID consultado não corresponde a um registro existente.
CONFLITOUm pedido já está fechado ou uma mesa já possui pedido aberto. A situação atual impede a operação.
INTERNOUm problema técnico na persistência impede concluir a operação. A mensagem destinada ao cliente deve ser controlada.

Para as categorias sem um método de criação específico, o código poderá usar o construtor, como new Falha("NAO_ENCONTRADO", Falha.Tipo.NAO_ENCONTRADO, "Registro não encontrado.").

Confira: o nome do arquivo e da classe é Falha, o pacote está correto e o editor não aponta erro de sintaxe.

Acompanhar um exemplo: criar uma Falha e lançá-la são ações diferentes

Exemplo de leitura para as próximas aulas. Este trecho pertence à futura regra que altera um pedido:

if (atual.situacao() != SituacaoPedido.ABERTO) {
    throw Falha.conflito(
        "PEDIDO_" + atual.situacao(),
        "Pedido " + atual.situacao().name().toLowerCase()
            + " não permite alterações."
    );
}
  1. Se o pedido estiver ABERTO, essa condição será falsa e o processamento continuará.
  2. Se estiver FECHADO, a condição será verdadeira. Falha.conflito(...) criará o objeto com código PEDIDO_FECHADO, tipo CONFLITO e a mensagem correspondente.
  3. throw lançará esse objeto. O fluxo normal sairá desse ponto até encontrar um tratamento compatível.
  4. O tratamento poderá consultar e.codigo(), e.tipo() e e.getMessage(). No sistema completo, essa tradução será feita pelos adaptadores.

Guarde a diferença: new Falha(...) e os métodos de criação produzem um objeto; throw é a instrução que o lança. Essa classe não elimina uma indisponibilidade do banco nem decide automaticamente qual operação é válida: ela padroniza como o problema é comunicado.

-pl :aplicacao -am compile

Se a compilação não der certo

Se aparecer “dominio … was not found … during a previous attempt”

Essa mensagem registra no repositório local uma tentativa anterior de obter o artefato no Central. Confira o início da saída: se aparecer somente Building aplicacao, o módulo local dominio não está sendo construído junto.

Para fixar explicitamente qual POM deve ser usado:

  1. Abra Run → Run Configurations… → Maven Build e selecione a configuração que você vai executar.
  2. Substitua todo o campo Goals pelo exemplo abaixo, ajustando o caminho para o POM pai do seu computador. O destino precisa ser o POM restaurante-soap, que lista os dois módulos.
  3. Clique em Apply e depois em Run nessa mesma janela.
-f C:/workspace/SOA/laboratorio-restaurante-soa/source/restaurante-soap/pom.xml -pl :aplicacao -am compile

-f escolhe diretamente o arquivo POM. -pl :aplicacao seleciona o artefato da aplicação e -am inclui as dependências presentes no reator, como o domínio. Assim, a seleção do POM pai fica explícita mesmo que a configuração tenha sido aberta a partir do filho. Referência oficial das opções Maven.

Na Console, confira restaurante-soap, dominio e aplicacao em Reactor Build Order. Se sua pasta se chama domino, mantenha <module>domino</module> no pai e confira <artifactId>dominio</artifactId> no filho, conforme o diagnóstico do nome da pasta.

Se aparecer “Child module …/dominio … does not exist”

O Maven já localizou o POM pai, mas não encontrou um dos módulos no caminho declarado. Cada entrada de modules aponta para uma pasta ou POM relativo ao pai. Confira a localização física do projeto no Eclipse: botão direito → Properties → Resource → Location. Como localizar projetos no Eclipse.

Exemplo: a pasta foi criada como domino, mas o POM declara dominio. São nomes diferentes; falta o segundo “i” em domino. Se você mantiver essa pasta, o pai deve apontar para o nome que existe:

<modules>
    <module>domino</module>
    <module>aplicacao</module>
</modules>

Confira também o filho: em domino/pom.xml, mantenha <artifactId>dominio</artifactId>, com grupo br.edu.soa e versão 2.0.0 herdados do pai. A dependência de aplicacao continua sendo br.edu.soa:dominio:2.0.0.

ValorO que identifica
<module>domino</module>A pasta real do módulo, relativa ao POM pai.
<artifactId>dominio</artifactId>O nome do artefato produzido pelo módulo e usado nas dependências.

Salve os POMs, use Maven → Update Project… e execute novamente -pl :aplicacao -am compile a partir do pai.

Os exemplos completos do curso usam a pasta dominio. Se você mantiver a pasta domino, preserve essa grafia na lista modules dos próximos POMs e adapte os caminhos correspondentes. Se padronizar a pasta como dominio, volte a entrada do pai para <module>dominio</module>. Apenas mudar o nome exibido no Eclipse pode não alterar a localização física; confira novamente Location.

Se o módulo ainda não tiver sido criado, retome a aula 13 e depois confira as classes construídas nas aulas 14–18. Uma pasta vazia não substitui o POM e os fontes do domínio.

E o aviso do Jansi sobre acesso nativo?

Na saída apresentada, o aviso identifica uma biblioteca usada pelo Maven e a execução continua até ler os POMs. O erro que interrompe esse build é o módulo ausente no caminho declarado. Confira também o JDK 17 na aba JRE da configuração Maven, conforme o ambiente adotado no curso.

Se aparecer “Could not find artifact br.edu.soa:dominio:jar:2.0.0 in central”

dominio é um artefato construído pelo seu projeto. Se somente aplicacao entrar no build e o domínio ainda não estiver no repositório local, o Maven tentará resolver essa dependência nos repositórios configurados e poderá procurar no Central.

Para a aula, compile os módulos juntos a partir do pai:

  1. Use File → Save All. No Project Explorer, selecione o projeto cujo POM contém <artifactId>restaurante-soap</artifactId> e <packaging>pom</packaging>.
  2. Clique com o botão direito nesse pai e escolha Run As → Maven build…. Confira novamente Base directory: deve ser a pasta que contém o POM pai e as pastas irmãs dominio e aplicacao.
  3. Confira <module>dominio</module> e <module>aplicacao</module> na lista modules desse POM.
  4. Use exatamente -pl :aplicacao -am compile em Goals e clique em Apply → Run. A opção -am inclui as dependências que pertencem ao mesmo reator; ela não reúne automaticamente módulos irmãos quando a execução parte somente do filho.
  5. Confirme a presença de dominio em Reactor Build Order, antes de aplicacao.

Se dominio continuar ausente: confira suas coordenadas. O POM de dominio deve resultar em br.edu.soa:dominio:2.0.0, o mesmo grupo, nome e versão exigidos pela dependência de aplicacao. Grupo e versão podem ser herdados do pai; o artifactId do filho precisa ser dominio.

Por que compilar dominio sozinho não resolveu?

compile produz classes em target/classes. package produz o JAR em target. A fase install também coloca o JAR e o POM no repositório local, para uso por outras execuções. Na configuração desta aula, -am reúne domínio e aplicação na mesma execução, permitindo compilar sem depender de uma instalação anterior do domínio. Referência: fases do Maven.

Se aparecer “Could not find the selected project in the reactor: aplicacao”

O Maven ainda não começou a compilar. O reator é o conjunto de projetos reunidos a partir do POM escolhido para essa execução. Esse erro informa que a seleção não correspondeu a um projeto desse conjunto.

  1. Em Run → Run Configurations… → Maven Build, abra a configuração desta aula. Em Base directory → Browse Workspace…, escolha restaurante-soap, a pasta que contém o POM pai e as subpastas dominio e aplicacao.
  2. Abra o pom.xml dessa pasta e confira o artifactId restaurante-soap, o packaging pom e as duas entradas de modules mostradas no passo 3. Ter o projeto visível no Eclipse, sozinho, não registra o módulo no build do pai.
  3. Confira a existência de aplicacao/pom.xml e o artifactId aplicacao nesse filho. O caminho da entrada module é relativo à pasta do POM pai.
  4. Salve com File → Save All, use Maven → Update Project… nos projetos envolvidos e repita com -pl :aplicacao -am compile. Se houver -N em Goals, remova-o: essa opção impede percorrer os módulos.

Sem os dois-pontos, -pl aplicacao procura o caminho relativo aplicacao. Com -pl :aplicacao, a seleção usa o artifactId. Em ambos os casos, o módulo precisa participar do reator da execução. Referência oficial: seleção de módulos no Maven.

  • Módulo não encontrado: confira a pasta aplicacao, seu POM, a lista modules e o projeto selecionado em Base directory.
  • Pai ou domínio não localizado: confira as coordenadas e a versão 2.0.0. Na configuração Maven desta aula, mantenha -am.
  • Versão ausente para JUnit/Mockito: confira a herança de restaurante-soap e a importação do BOM em dependencyManagement.
  • Erro em Falha.java: confira pacote, nome do arquivo e a chamada super(mensagem) no construtor.
  • Após mudar um POM, salve e use Maven → Update Project…. Leia a mensagem específica em Problems ou na Console.

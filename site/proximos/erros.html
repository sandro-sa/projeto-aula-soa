Resolver problemas do laboratório

Investigar uma falha reproduzível e registrar o diagnóstico e a correção.

1. O que fazer nesta etapa

Investigar uma falha reproduzível e registrar o diagnóstico e a correção.

Esta aula é uma atividade de execução, análise ou registro sobre o sistema já construído.

A aula termina quando: O registro contém sintoma, evidência, causa, correção e uma nova verificação.

Continue no Eclipse após Comparar SOAP e REST construídos. Use os projetos e os arquivos que você construiu nas etapas anteriores.

2. Entenda o que será feito

O sintoma indica onde começar; confirmar a causa exige observar a camada, a configuração e os registros corretos.

  • Não inclua senhas, cabeçalhos Basic ou strings de conexão com credenciais nas evidências.
  • Use a Console, Problems, relatórios Maven e a resposta HTTP/SOAP para separar as camadas.
Pontos para observar no código
  • Falha separa código técnico estável de mensagem de usuário.
  • A infraestrutura registra SQLState/código, sem enviar a mensagem SQL ao cliente.
  • O fluxo de diagnóstico parte de versões/conectividade e avança para contrato/regra.

3. Faça o passo a passo

Passo 1: Executar a atividade e registrar a evidência

  1. Escolha um erro que você observou e anote como reproduzi-lo. Se nenhum ocorreu, execute no Swagger uma consulta protegida, como GET /api/mesas, com uma senha incorreta e confira a resposta 401.
  2. Leia a Console, a aba Problems e, quando houver teste, o relatório de target/surefire-reports. Copie apenas a mensagem útil, sem credenciais.
  3. Classifique a camada: build/configuração, conexão, publicação, contrato, autorização ou regra de negócio.
  4. Corrija a causa identificada e repita o mesmo procedimento. Registre a evidência da correção.
SintomaPrimeira conferência
Propriedade de versão não resolvida no MavenNome declarado em properties e referência com a mesma grafia.
401 / 403Identidade e papel exigidos pela rota.
404Aplicação publicada, contexto e caminho solicitado.
Conexão recusada / acesso negado ao bancoServiço/porta ou usuário/host/senha/permissões, conforme a mensagem.
Checksum FlywayPreservar a migração aplicada e criar nova versão para nova mudança.

Registre a verificação no arquivo docs/registro-laboratorio.md. No projeto laboratorio-restaurante, use New → File se ele ainda não existir; nas próximas atividades, acrescente a nova aula ao mesmo registro.

4. Resultado esperado

O registro contém sintoma, evidência, causa, correção e uma nova verificação.

Se a verificação não der certo
  • Leia a mensagem específica na Console ou na aba Problems; confira o projeto, o caminho do arquivo e o pacote.
  • Depois de mudar POMs, use Maven → Update Project…. Confira se cada módulo listado já possui seu POM.
  • No Maven build, confira Base directory, Goals e o JDK 17. Em erro de download, confira a conexão e o repositório informado.
  • Em problema de execução, diferencie configuração do processo, conexão com o banco, rota/contrato e regra de negócio. Consulte a aula de diagnóstico.

Fundamentação nos PDFs fornecidos

Use a evidência da camada para interpretar o problema: erro de ambiente, recusa de negócio, status HTTP e Fault XML têm significados diferentes. A referência bibliográfica não substitui a reprodução do erro no ambiente do aluno.

  • [R06] Guilherme Silveira; Mário Amaral — Java SE 7 Programmer I: o guia para sua certificação Oracle Certified Associate. Cap. 10, §10.1–10.2: checked, runtime e tratamento. Páginas 336–339 do PDF.
  • [R02] Alexandre Saudate — REST: construa APIs inteligentes de maneira simples. Cap. 2, §2.6: códigos de status. Páginas 29–32 do PDF.
  • [R01] Alexandre Saudate — SOA aplicado: integrando com web services e além. Cap. 3, §3.2–3.4: exceções, Fault e detail. Páginas 60–65 do PDF.
